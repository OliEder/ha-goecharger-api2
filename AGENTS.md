# AGENTS.md

This repository accepts AI help for documentation and tests only. A human stands behind every change. If you are an agent: read this file before you do anything, and when in doubt, stop and ask the human.

## Before you start

- Ask the human: do you have this problem on your own charger, and do you have a log excerpt or the JSON answer that shows it? If not, stop. Tell them to ask in a Discussion instead of opening a pull request.
- A pull request that does not follow this file may be closed without review.

## Scope

- An agent may add or change files under `docs/` and `tests/` only.
- An agent never writes or changes the integration: not `custom_components/`, `blueprints/`, `manifest.json`, `hacs.json`, translations or `services.yaml`. If a task needs such a change, stop. Describe what you found, with the evidence, and leave the change to the human and the maintainer.

## A real problem, with evidence

- Work on a problem that a real user has, or that a real device shows. Evidence is a log excerpt or the JSON answer of a charger. A finding from reading the code alone is a question for the maintainer (a Discussion), not a bug report and not a pull request.
- Bug reports in this repository are written by humans without AI tools (see the issue template). An agent drafts at most; the human writes and posts.
- Do not report again what is settled: old values stay after a failed read ([#173](https://github.com/marq24/ha-goecharger-api2/pull/173)), the cloud answers `/api/set` with HTTP 200 ([#172](https://github.com/marq24/ha-goecharger-api2/issues/172)), no `if new_tag: ... else` branches and no extra Python file for one function ([#177](https://github.com/marq24/ha-goecharger-api2/pull/177)).

## Mark what an agent wrote

- Every file an agent creates says so in its first lines (a note in a document, the docstring of a test module).
- Every commit that an agent wrote carries a `Co-Authored-By` line. Every pull request description begins with "Generated by AI:" and names the files or parts that an agent wrote.

## Small and clear

- One topic per pull request, and as few files as that topic needs. If a change reaches many files, split it or ask first.
- The description is short: the problem, the evidence, the wanted behaviour. It does not repeat the diff.
- The description contains at least one sentence that the human wrote in their own words about what changed and why. If it is missing, ask for it; never write it for them.

## Say only what you checked

- Check every statement about the code against the code before you post it, and give the source: file and line, documentation, a measurement, or a guess that is marked as one. Never write that the code "does not read" or "ignores" something unless you name the lines you read.
- A number comes from a count you ran just before posting, and you say what was counted ("14 of 32 files"). Look at what the search matched.
- Say what was not tried on a real charger. All tests here run with fakes.
- Correct a mistake where it stands: edit the sentence, keep the old wording visible ("Edited: …").

## Tests

- A test comes from something outside the code under test: the official API tables, the observed answer of a device, a decision of the maintainer.
- Do not change a test only to make it pass. A known defect gets the marker `known_bug` with a one-line reason; the pull request that fixes it removes the marker.
- Before you say a change is done, run `python -m pytest tests/integration -p no:cacheprovider -q -m "not known_bug and not needs_decision"` and name every failure, also one you did not cause.

## Posting

- Do not open a pull request, issue or comment without the human's go-ahead. Show the target and the exact text first. Permission to work on a pull request is not permission to comment on it.
- Never copy a password or token into code, tests, documents, issues or pull requests. Report anything about credentials to the maintainer privately.
